# AHDG-0001 — Security state survives return to the default session

| Field | Value |
|---|---|
| ID | AHDG-0001 |
| Layer | UDS (SecurityAccess × DiagnosticSessionControl) |
| Invariant | `SEC_RELOCK_ON_DEFAULT` (SEC-4) |
| Discovered by | `fuzz/ahdg_explore.c` — adversarial state-space explorer |
| Discovery mode | automatic, not hand-written |
| Seed | `0xA11CE` |
| Class | cross-layer state confusion (security ↔ session) |
| Status | fixed, regression added, re-attacked clean |

## What it is

The adversarial explorer, driving the real `src/uds/uds.c`, reached a **forbidden
state**: security unlocked while the session was the default session. It was not
looking for this specific bug — it was searching the combined state space for
any invariant violation, and found this one on the first campaign.

## Minimal counterexample

Reduced by delta-debug from a longer sequence to **four actions**:

```
1. session extended         (10 03)   session: DEFAULT -> EXTENDED
2. security: request seed    (27 01)   seed issued
3. security: send correct key(27 02 K) security: LOCKED -> UNLOCKED
4. session default           (10 01)   session: EXTENDED -> DEFAULT
```

Observed state after step 4, before the fix:

```
session   : DEFAULT
security  : UNLOCKED      <-- violation
seed      : none
```

## Root cause

`handle_diagnostic_session_control` set `ctx->session = DEFAULT` on a `10 01`
request but did **not** relock security. The server relocked security only on
two other paths — the S3 timeout in `uds_poll` and `ECUReset` — and never on an
explicit return to the default session. The security level therefore carried
over from the extended session into the default session.

## Impact — stated honestly

This is a **latent state confusion, not a demonstrated privilege escalation in
the current service set.** In this server every security-gated service is also
gated on the extended session, so in the default session `ECUReset` is refused
by the session check (`serviceNotSupportedInActiveSession`) *before* the security
check is reached. Defense-in-depth masks the direct exploit today.

It matters nonetheless, and is worth a fix and a permanent test, because:

- it is a genuine violation of a stated invariant — a state the design declares
  impossible was reachable;
- any future service gated on security alone (not session) would be directly
  exposed;
- it is exactly the cross-layer class the project targets: authority from one
  context (extended session) leaking into another (default session). The general
  lesson generalizes beyond this one sequence.

Per ISO 14229 the correct behavior is unambiguous: SecurityAccess is only valid
in a non-default session, and entering the default session returns the server to
its power-on diagnostic state — which is locked.

## Fix

Relock on any transition to the default session:

```c
case (uint8_t)UDS_SESSION_DEFAULT:
    ctx->session        = UDS_SESSION_DEFAULT;
    ctx->security_level = UDS_SECURITY_LOCKED;
    ctx->seed_pending   = 0u;
    break;
```

## Regression

Encoded as a permanent, self-contained test in `tests/test_uds.c`
(`test_security_access`, block "Regression AHDG-0001"): unlock legitimately in
the extended session, return to the default session, assert security is
`LOCKED` and no seed lingers.

## Re-attack

After the fix, the explorer was re-run for 1,000,000 sequences on the discovery
seed `0xA11CE` and 1,000,000 on an independent seed `0xBEEF42`: **zero
counterexamples** for SEC-4 and for the five other invariants it evaluates. The
count of reachable security states dropped from 10 to 8 — the fix removed the
forbidden `DEFAULT × UNLOCKED` combinations, not merely hid them.

## Reproduce

```bash
git checkout 1133d39 -- src/uds/uds.c   # the state before the fix
make explore                            # ./build/ahdg_explore prints the counterexample
git checkout HEAD -- src/uds/uds.c      # restore the fix
make explore                            # zero counterexamples
```
